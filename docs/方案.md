# codex-workbuddy-subagent 方案

## 1. 目标与成功标准

### 目标

把现有的 **WorkBuddy Bridge 1.0.1**（MCP 插件 + WorkBuddy `codebuddy` CLI 执行层）扩展成一个可安装、可验证的 **codex-workbuddy-subagent**：

- Codex 主任务保持现有模型 / provider 不变；
- Codex 原生生成一个独立 child task，agent type 为 `workbuddy_worker`；
- 父 Agent 用一次性 plaintext assignment 交付任务；
- child 通过 WorkBuddy Bridge 的执行层调用 `codebuddy`，返回结构化结果；
- 写操作继续受 TaskSpec v1、scope guard、worktree 锁、审计和审批约束。

### 成功标准

1. 新开 Codex 任务后，`workbuddy_worker` 可被发现并原生 spawn；
2. `fork_turns="none"` 的 child 能收到父 Agent 通过 Hook 注入的完整 assignment；
3. child 能执行 `plan`（只读）与已确认的 `execute`（受限写）并返回结果；
4. 父 Agent 收到 child 原样返回的随机 marker，证明任务确实走 Hook 交付；
5. 主任务模型 / provider 不改变；
6. 不绕过 bridge 的 scope、worktree 锁、审计、审批或输出边界；
7. 提供本地协议测试、安装校验脚本和 smoke test，而不是只有文档。

## 2. 两个上游的分析结论

### 2.1 codex-deepseek-subagent

仓库提供的是“原生 custom agent + lazy skill + one-shot plaintext Hook”组合：

- `agents/v4-flash-worker.toml`：独立 child session 配置，自带 `model_provider` 和 `[model_providers.deepseek]`；
- `skills/use-v4-flash-worker/SKILL.md`：父 Agent 按需加载的委派协议；
- `hooks/plaintext_handoff.py` / `plaintext-handoff.ps1`：staging + `SubagentStart` Hook，把 assignment 以 developer context 注入 child；
- `hooks/hooks.posix.example.json` / `hooks.windows.example.json`：Hook 结构；
- `snippets/AGENTS.md`：两条 `$use-v4-flash-worker` 索引；
- `prompts/install-with-codex.md`、`quick-smoke-test.md`、`smoke-test.md`、`message-handoff-probe.md`：安装合同与验证；
- `tests/test_plaintext_handoff.py`：27 项协议测试，覆盖原子发布、单次消费、并发、损坏状态保留、过期恢复等；
- 文档说明：macOS/POSIX 在 Codex `0.146.0` 通过 callback smoke 和 27 项协议测试。

它解决的核心问题是：OpenAI parent 向非 OpenAI child 交付 Multi-agent V2 任务时，collaboration 参数可能变成 provider-internal ciphertext，child 看不到 `Payload:`。该仓库用受信任 Hook 绕过这个表示问题，而不是切换主模型或引入 MCP / 插件。

### 2.2 WorkBuddy Bridge 1.0.1

WorkBuddy Bridge 是“Codex 插件 + Node MCP server + WorkBuddy CLI”：

- `.codex-plugin/plugin.json` 与 `.mcp.json` 声明插件；
- `mcp-server/src/*.ts` 实现 stdio MCP server，暴露 10 个工具：health、plan、execute、plan_start、execute_prepare、execute_start、batch_start、task_status、batch_status、task_cancel；
- `TaskSpec v1` / `ResultEnvelope v1` 是稳定任务契约；
- `ExecutionGuard` 在 execute 前后做 bounded snapshot，返回 created / modified / deleted / changed_files / changed_bytes / coverage；
- `workspace-identity.ts` 识别 Git 仓库与 linked worktree，提供 worktree-aware lock key；
- `approval.ts` 为 background execute 生成 HMAC 签名、短时、单次 token；
- `background-plan-manager.ts` + `task-store.ts` 提供 SQLite 持久任务、batch、事件游标和 `orphaned` 状态；
- `audit-log.ts` 写 metadata-only 审计；
- `result-adapter.ts` 解析 JSON / JSON array / NDJSON，失败只返回 bounded diagnostics 和 SHA-256；
- `capability-probe.ts` / `version.ts` 做 CLI 能力和版本握手。

本机实测事实：

- `codebuddy` 位于 `/Applications/WorkBuddy.app/Contents/Resources/app.asar.unpacked/cli/bin/codebuddy`，版本 `2.115.0`；
- `codebuddy --help` 显示支持 `--print`、`--output-format json|stream-json`、`--permission-mode`、`--tools`、`--max-turns`、`--no-session-persistence`、`--strict-mcp-config`、`--serve`、`--acp`；
- Codex CLI 为 `0.147.0-alpha.6.5`；
- `workbuddy-bridge@wuyi-personal` 已存在于个人 marketplace，但状态为 `not installed`；
- `~/.codex/workbuddy-bridge/tasks.sqlite3` 已存在；
- `~/.codex` 当前没有 `agents`、`hooks` 或 `hooks.json`，是干净的安装基线。

### 2.3 为什么不能直接照搬 deepseek 的做法

DeepSeek 能直接作为 child provider，是因为它暴露 Codex 支持的 Responses wire API。WorkBuddy CLI 本身是 agent CLI，不是 Responses / Chat Completions 端点；`--serve` 和 `--acp` 属于另一套协议。因此 v1 不应试图把 `codebuddy` 伪装成 model provider，而应把 WorkBuddy Bridge 保留为执行引擎，在其外层加一个 Codex 原生 subagent 入口。

## 3. 推荐架构（v1）

```
Codex 主任务（现有模型/provider）
  -> 加载 $use-workbuddy-worker
  -> stage 一个自洽 assignment 到本地 state
  -> native spawn_agent: workbuddy_worker, fork_turns="none"
  -> SubagentStart Hook 原子 claim 并注入 developer context
  -> child 解析 assignment，调用 WorkBuddy Bridge MCP 工具
  -> bridge 校验 cwd / scope / worktree / CLI 能力
  -> codebuddy CLI 执行 plan 或受限 execute
  -> bridge 返回 ResultEnvelope v1 + 变更证据
  -> child 原样返回 marker 与结果
  -> 父 Agent 独立验证、整合
```

关键决策：**保留 MCP Bridge 作为执行层，不拆成 child 直接 shell 调 CLI**。原因：

- MCP server 进程在 Codex sandbox 之外运行，child 自身可以保持 `read-only`，写权限由 bridge 的 scope guard 控制；
- 现有 10 个工具、审批 token、background task、batch、audit 全部复用，不需要重写；
- child 只负责“接收 assignment -> 调用正确工具 -> 返回结果”，模型成本与失败面都小。

## 5. 安装与运行流程

### 5.1 前置安装

1. 安装 WorkBuddy Bridge 插件：

```sh
codex plugin add workbuddy-bridge@wuyi-personal
```

2. 用 `scripts/diagnose-workbuddy.sh` 或 `codebuddy --version` 确认 CLI 可用（本机已确认 `2.115.0`）。

### 5.2 子 Agent 模型选择

`workbuddy_worker` 是 Codex session，必须配置自己的模型 / provider。推荐顺序：

1. 默认复用当前主任务 provider，但选择更便宜的模型（例如本机 `opencode_go` provider 下的 `deepseek-v4-flash`）；
2. 如果已有 `DEEPSEEK_API_KEY`，可照 deepseek 模板使用独立 DeepSeek provider；
3. 安装器只读取当前配置结构，不打印、不复制真实 secret；需要 secret 时改用 `env_key` 或 command auth。

### 5.3 安装 subagent

复制 `prompts/install-with-codex.md` 给 Codex 执行，流程包括：

1. 检查 `CODEX_HOME`、目标 `agents/`、`skills/`、`hooks.json`、`AGENTS.md`；
2. 安装 `agents/workbuddy-worker.toml`；
3. 安装 `skills/use-workbuddy-worker`；
4. 安装 `hooks/codex-workbuddy-subagent/plaintext_handoff.py`；
5. 合并一条 `SubagentStart` Hook，matcher 为 `^workbuddy_worker$`；
6. 合并 `snippets/AGENTS.md` 到个人 `AGENTS.md`；
7. 不伪造 `hooks.state` trust hash；
8. 本地协议测试通过后停止，不自动跑 smoke。

### 5.4 信任与测试

1. Codex 输入 `/hooks`，确认 Hook 只匹配 `workbuddy_worker` 并信任；
2. 新开一个 Codex 任务；
3. 执行 `prompts/quick-smoke-test.md`，验证：

- 出现独立原生 child，agent type 为 `workbuddy_worker`；
- child 返回父 Agent 的随机 marker；
- pending handoff 被消费；
- child 通过 bridge 完成一次只读 `workbuddy_plan`；
- 主任务 provider / 模型不变。

## 7. 实施阶段

1. **Phase 0 决策**：确认版本号、child 模型来源、是否保留 background / batch 工具暴露；
2. **Phase 1 脚手架**：把 `/Users/wuyi/plugins/workbuddy-bridge` 或 zip 解包内容复制为 `codex-workbuddy-subagent`，更新插件元数据与版本；
3. **Phase 2 新增工件**：写 `agents/workbuddy-worker.toml`、skill、hook 适配、AGENTS.md 索引、prompts、docs；
4. **Phase 3 测试**：移植 deepseek 27 项协议测试，跑 bridge 全套测试，跑安装校验；
5. **Phase 4 本地安装**：安装插件与 subagent，`/hooks` 信任，新任务跑 quick smoke 和写 smoke；
6. **Phase 5 未来项**：评估 `codebuddy --acp` / `--serve` 是否能做成本地 Responses adapter，从而去掉 MCP 依赖，让 WorkBuddy 直接作为 child provider。

## 8. 风险与待确认

| 事项 | 风险 / 影响 | 建议 |
| --- | --- | --- |
| 是否保留 MCP 插件 | 保留更安全但不如 deepseek 那样“无 MCP”；拆 runner 则 child 需要写 sandbox | v1 保留插件 |
| child 模型来源 | 复用主 provider 无新凭据，但模型价格 / 能力受代理影响；DeepSeek 直连需 API key | 安装时按当前 provider 生成，不写死 |
| 版本号 | 新增 native subagent 属于功能变化 | 建议 `1.1.0+codex...`，保留 1.0.1 兼容 |
| Windows | 需要移植并实测 PowerShell Hook 与 bridge | 本机只验证 macOS |
| WorkBuddy 数据边界 | assignment、工具结果会进入 WorkBuddy 的模型服务 | 文档明示，用户授权后才委派敏感材料 |
| Codex alpha | `0.147.0-alpha.6.5` 仍可能有 V2 ciphertext 问题 | 一律走 Hook 交付，不用继承 turns 兜底 |
| 已有 SQLite 状态 | `~/.codex/workbuddy-bridge/tasks.sqlite3` 存在，插件未安装 | 安装后先 health，不自动清理遗留状态 |

## 9. 结论

推荐方案是“**deepseek 式原生 subagent 入口 + WorkBuddy Bridge 1.0.1 执行层**”：新增 `workbuddy_worker` native child 和 one-shot Hook 交付，child 内部通过 bridge MCP 工具调用 `codebuddy`，保留全部安全边界。该方案工作量集中在新增 agent / skill / hook / prompts / 测试，bridge 执行层无需重写，风险可控；真正把 WorkBuddy 变成 Codex model provider 需要未来基于 `--acp` 的本地 adapter，不进入 v1。
